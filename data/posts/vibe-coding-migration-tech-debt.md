## TL;DR

- 100% 바이브 코딩(Vibe Coding)으로 만든 개인 플래너를 ES 모듈과 SvelteKit으로 이주했다.
- 계기는 "AI가 코딩을 해결했다면 왜 소프트웨어는 그대로인가"라는 영상이었다. AI가 쌓은 코드가 정말 기술 부채인지 확인하고 싶었다.
- 구조는 깔끔해졌다. 하지만 기존 동작을 목록으로 만들지 않고 "옮겨 줘"로 진행해서 기능이 빠졌고, 배포하자마자 기존보다 느려졌다.
- 바이브 코딩의 기술 부채는 코드 모양보다 **어디에도 적혀 있지 않은 동작**에 쌓여 있었다.

## AI가 코딩을 해결했다면 왜 내 소프트웨어는 그대로일까?

이 질문을 던진 사람은 Jonathan Blow다. 그의 답은 이렇다. AI는 코드를 빠르고 싸게 만들지만, 사용자가 쓰는 소프트웨어가 눈에 띄게 좋아졌다는 증거는 아직 없다. GeekNews에 올라온 [영상 요약](https://news.hada.io/topic?id=37150)을 보고 알게 됐다.

처음에는 무슨 말인가 싶었다. 옆에서는 Claude가 코드를 너무 많이 만들어서 git으로 관리하기 어렵다는 이야기가 나오고, 새로운 코드 관리 도구까지 나오는 상황이었다. 생산성이 폭발하고 있는데 산업이 그대로라니 이상하게 들렸다.

그런데 요지를 따라가 보니 이해되는 부분이 많았다.

- 그가 말하는 생산성은 생성한 코드의 양이 아니라 **제품이 실제로 얼마나 달라졌는가**다. 요약은 이를 "생산성 향상 주장과 실제 제품 변화"를 구분해야 한다고 정리한다.
- AI는 같은 문제를 풀 때 숙련된 사람보다 코드를 더 많이 만드는 경향이 있다. 그렇게 늘어난 코드는 다음 변경을 할 때 유지보수 부담이 된다.
- 낡은 설계 위에 기능을 계속 쌓으면 복잡도와 변경 비용이 올라간다. AI가 같은 문제에 코드를 더 만들어 주면 이 흐름이 더 빨라질 수 있다.
- AI가 중요한 기술 발전인 것과, AI가 일반 소프트웨어 제작에 가져온 성과는 다른 문제다.

그래서 내가 바이브 코딩으로 만든 것들을 다시 돌아봤다.

## 바이브 코딩으로 만든 플래너는 어떤 구조였나?

가장 잘 쓰고 있는 앱은 개인 플래너다. 캘린더와 할 일을 읽고 "지금 이 시간에 무엇을 할지"를 고르게 도와주는 페이지 하나다. 코드는 100% AI가 썼다. 나는 원하는 것만 말했다.

다시 열어 보니 구조가 이상했다. 처음에 Claude 아티팩트(Artifact)로 만든 것을 웹으로 옮긴 앱이라서 그 흔적이 그대로 남아 있었다.

```text
./planner deploy (bash)
  └─ node build.mjs
       ├─ src/page.html 안의 표시 줄을 찾아서
       ├─ src/js/00-config.js … 18-boot.js (23개, 약 3,500줄)를
       │    파일 이름 순서대로 이어 붙여 함수 하나로 감싸고
       └─ Supabase 접근 코드를 "가짜 MCP"로 끼워 넣어
            dist/index.html 한 장을 만든다 → Vercel
```

- **아티팩트는 HTML 파일 하나만 올릴 수 있었다.** 그래서 JS를 `import` 없이 이어 붙였다.
- **이어 붙이는 순서가 곧 의존성이었다.** 파일 이름 앞에 `00-`, `05-`, `17-` 같은 숫자가 꼭 붙어 있어야 했다. 앞 파일에서 정의한 값을 뒤 파일이 그냥 가져다 썼다.
- **데이터 접근은 아티팩트 시절 모양 그대로였다.** 화면 코드는 `mcp.callTool('할 일', …)`을 불렀고, 중간 계층(shim)이 그 호출을 Supabase 쿼리로 바꿔 줬다.

단순하긴 했다. bash 스크립트 하나로 빌드와 배포가 끝났다. 하지만 어떤 변수가 어디서 왔는지 코드만 봐서는 알 수 없었다.

## 파일 이름 앞의 숫자는 기술 부채였을까?

반은 맞았다. 파일 이름의 숫자는 그 자체로 문제였다기보다, **아티팩트라는 제약이 사라진 뒤에도 남은 우회책**이었다. 제약이 없어졌는데 우회책만 남으면 이유를 모르는 규칙이 된다. [기술 부채](/posts/technical_debt)가 쌓이는 전형적인 모양이다.

이번 이주의 목적은 두 가지였다.

1. 내가 매일 쓰는 코드를 제대로 이해하기
2. AI가 구조적으로 코드를 잘 짜는지에 대한 의구심을 직접 확인하기

## 이주는 어떤 순서로 했나?

한 번에 다시 짜지 않고 네 단계로 나눴다. 단계마다 커밋하고 바로 배포했다.

| 단계 | 한 일 | 결과 |
|---|---|---|
| 1 | Vite 개발 서버 붙이기 | push 없이 `localhost`에서 바로 확인 |
| 2 | `./planner` bash 래퍼를 npm 스크립트로 | `npm run dev · build · test · deploy` |
| 3 | 이어 붙이던 23개 파일을 ES 모듈로 | 파일마다 `import`/`export`가 명시됨 |
| 4 | SvelteKit + TypeScript + Tailwind + Zod + Vitest로 다시 쓰기 | 다섯 탭 이주, 약 4,600줄, 테스트 7개 → 59개 |

3단계는 생각보다 덜 아팠다. 파일 사이 참조를 AST(추상 구문 트리)로 분석해 보니, 자동 변환이 안 되는 곳은 세 군데뿐이었다.

- 다른 파일에서 값을 다시 대입하던 변수 하나(`mcp = m`). ES 모듈의 import는 읽기 전용이라 setter를 둬야 했다.
- 다른 파일의 타이머 상태를 직접 바꾸던 토스트 코드.
- 로드 순서에 기대던 상수 하나. 순환 import에 걸리면 초기화 전 접근(TDZ) 오류가 난다.

이 정도면 AI가 짠 구조가 엉망이었던 건 아니다. 제약 아래서는 합리적인 선택을 했고, 제약이 사라진 뒤 아무도 그 선택을 다시 보지 않았을 뿐이다.

## 다시 짰더니 왜 기존과 똑같이 동작하지 않았을까?

4단계에서 느낌이 완전히 달라졌다. 코드는 깔끔해졌는데 **앱은 기존과 100% 같게 동작하지 않았다.** 이유는 "이 화면을 SvelteKit으로 옮겨 줘"처럼 화면 단위로 시켰기 때문이다. 기존 코드가 하고 있던 일을 목록으로 만든 적이 없으니, 무엇이 빠졌는지 확인할 기준도 없었다.

중간중간 빠진 것이 많았다. 그중 기록해 둔 것만 적어도 이렇다.

- 테마 고르기: 기존에는 디자인 시스템 테마를 골랐는데, 새 앱은 기본색과 OS 다크 모드만 따라간다.
- "해결함"으로 기록하면 예전 "다음에 이어서:" 줄을 자동으로 완료로 바꾸던 동작이 빠졌다.
- 일기 화면은 전체 기간을 보여 줬는데, 속도 때문에 최근 180일로 줄었다.
<!-- 보강: 실제로 써 보며 발견한 누락 기능을 더 적기 -->

스택을 고를 때도 비슷한 일이 있었다. 처음 받은 스택 제안에는 SQLite와 Drizzle ORM이 들어 있었다. 그런데 Vercel 서버리스는 파일 DB를 계속 들고 있을 수 없어서 SQLite는 처음부터 맞지 않았다. Drizzle은 DB 비밀번호가 하나 더 필요하고 행 수준 보안(RLS)을 건너뛰는데, 나는 Drizzle이 무엇인지도 모른 채 넣었다. 결국 원래 쓰던 supabase-js로 돌아갔다. **내가 이해하지 못한 선택은 그대로 다음 부채가 된다.**

배포 직후에는 기존보다 훨씬 느렸다. 원인은 두 가지였다.

- 서버 함수가 기본값인 미국 동부 리전에서 돌았다. 페이지 하나를 그릴 때마다 한국 쪽 DB에 여러 번 순서대로 물어봐서 태평양을 몇 번씩 왕복했다.
- 기존 앱이 브라우저에서 한 번 읽어 들고 있던 작업 로그 전체를, 새 앱은 페이지를 열 때마다 서버에서 다시 읽었다.

함수를 서울 리전으로 옮기고 화면마다 필요한 기간만 읽게 해서 고쳤다. 하지만 이것도 결국 같은 이야기다. **기존 앱이 왜 빨랐는지가 어디에도 적혀 있지 않았다.**

## 검토한 대안: 다시 한다면 어떻게 이주할까?

### 1안: 화면 단위로 "옮겨 줘" (이번에 한 것, 버림)

빠르다. 하루 만에 다섯 탭이 다 옮겨졌다. 하지만 완료 기준이 "화면이 뜬다"여서 숨은 동작이 빠졌다. 이번에는 로그인하지 않고 확인할 방법이 없어서, 가짜 데이터로 서버 렌더링이 터지지 않는지만 검사했다.

### 2안: 기존 동작 목록을 먼저 만들고 스킬로 하나씩 매핑 (다음에 할 것)

기존 코드를 읽어 "이 앱이 하는 일" 목록부터 만든다. 버튼 하나, 자동 처리 하나까지 적는다. 그다음 항목마다 새 코드의 위치와 테스트를 짝짓는다. 반복되는 확인은 스킬로 만들어 매번 같은 기준으로 점검한다. [스펙 주도 개발(SDD)](/posts/spec-driven-development)에서 말하는 스펙이 이주에서는 이 동작 목록이다. 문서를 먼저 쓰는 방식이 [워터폴의 귀환](/posts/spec-driven-development-waterfall)처럼 보일 수 있지만, 이주는 이미 돌아가는 앱이 정답지라서 목록을 만드는 비용이 훨씬 작다.

### 3안: 옛 앱과 새 앱을 나란히 두고 조금씩 바꾸기

스트랭글러 패턴(Strangler Fig)처럼 기능 하나씩 새 앱으로 넘긴다. 가장 안전하지만, 혼자 쓰는 앱에 두 벌을 유지하는 비용이 크다.

## 결과: AI가 짠 코드는 기술 부채였나?

절반만 그렇다.

- **구조**는 생각보다 멀쩡했다. 이상해 보였던 숫자 파일 이름은 사라진 제약의 흔적이었고, 자동 변환이 안 된 곳은 세 군데뿐이었다.
- **진짜 부채는 기록되지 않은 동작**이었다. AI에게 말로 시키고 결과만 받으면, 왜 그렇게 동작하는지는 코드 안에만 남는다. 이주는 그 코드를 버리는 일이라 동작도 같이 사라진다.
- Blow가 설계 이유를 기록하는 역할을 따로 두자고 한 것도 같은 이야기로 읽힌다. 바이브 코딩에서는 그 역할이 아예 비어 있다.

그래서 이번에 얻은 결론은 "AI는 구조를 못 짠다"가 아니다. **AI와 만든 앱일수록 무엇을 하는지 목록부터 남겨야 한다**는 것이다. 다음 이주는 2안으로 다시 해 볼 생각이다.
